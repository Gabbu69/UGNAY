# Defense Walkthrough

This walkthrough demonstrates the thesis contribution without claiming that an algorithm makes academic decisions. Use a clearly labelled synthetic project locally; use institutional evidence only after its visibility and consent rules are confirmed.

## Before the panel

1. Start the same-origin JAR on `127.0.0.1:8080` and sign in with the temporary local administrator account.
2. Show the health endpoint, the visible `SYNTHETIC_DEMO` label, and the 512 MB Java heap configuration.
3. Keep this repository commit, the test ledger in `acceptance-and-demo.md`, and the current GitHub Actions run available as reproducibility evidence.
4. State the hardware boundary accurately: current-machine measurements verify function and packaging; Pentium/4 GB timing remains pending until captured on that physical laptop.

## Ten-minute canonical demonstration

1. **Problem and intake:** create one problem through the five-stage Intake Studio. Submit twice with the same idempotency key to show that only one problem, proposal, and discovery run exist.
2. **Related studies:** open the frozen discovery run. Explain field evidence, algorithm version, confidence state, and restricted-text redaction. Do not describe catalogue browsing as a similarity score.
3. **Human route:** select the exact proposal, run, and candidate. Show the separate machine recommendation, immutable adviser recommendation, and coordinator disposition. Explain that no first-record fallback exists.
4. **Objectives through outputs:** open the project-scoped Alignment Workspace. Switch between matrix/list and graph, then create one ETag-protected trace mutation. Show `428` for a missing precondition and the successful mutation with the current ETag.
5. **Controlled change:** add a typed change operation, preview its impact, then change the operation and demonstrate that the prior preview cannot be approved.
6. **Completion evidence:** show typed references, a missing numeric value rendered as `UNASSESSED`, independent verification, server-derived readiness, test currency, limitations, repository/setup rights, and exactly-one catalogue publication on repeat completion.
7. **Research review:** request one revision, respond as a project member, then show the immutable actor/time/evidence history and stale-ETag protection.
8. **Continuity:** claim one explicit predecessor objective with a rationale. Show that predecessor history remains append-only.
9. **Research Laboratory:** parse one RQL statement, inspect its AST and typed plan, show the latest warehouse snapshot, then explain the frozen four-arm evaluation protocol. Leave metrics `UNASSESSED` unless a real reviewed corpus and qrels exist.

## Questions the system must answer honestly

- **Does UGNAY detect plagiarism?** No. It retrieves and explains related evidence; authorized humans decide the academic route.
- **Why MySQL rather than a vector database?** MySQL remains the auditable source of truth at the measured pilot scale; Java performs bounded scoring and traversal.
- **What happens without the ONNX model or enough memory?** Semantic evidence becomes unavailable and the run is `PARTIAL`; lexical weights are not inflated.
- **Can a hidden study leak through a score?** Protected text may influence an authorized calculation, but unauthorized responses redact or omit identifiers, titles, and excerpts.
- **Why is Research Laboratory part of the thesis?** It makes the interpreter, warehouse pipeline, and retrieval evaluation reproducible. It cannot write an academic decision.
- **Is 4 GB proven?** Only after the physical Pentium/4 GB acceptance run. Configuration and concurrency controls support the target, but they are not a substitute for measurement.

## Stop conditions

Do not present the build as defense-ready if GitHub Actions is red, the browser console has errors, a project mutation bypasses `If-Match`, missing evidence is rendered as zero, or the local process is not the exact verified JAR hash.
